# Initial setup and model selection

Use this during first installation, reinstallation, or an explicitly requested backend/model change. Reuse choices already provided in this chat. Ask only for missing selections before starting a model request.

1. Inspect the installed Node, Git and selected Pi/DSH executables. Read only non-secret provider/model metadata from existing configuration; do not print credential files, keys or tokens. Before invoking Pi (including `pi --help` or `pi-bridge setup --apply`), account for Pi's first-run state initialization: Pi may create a short-lived lock directory for `trust.json` under its agent state directory, normally `~/.pi/agent`. If the host uses approval-gated filesystem access, allow this specific Pi startup operation to create and remove its lock there. Do not grant broad write access to the home directory. If the Pi state directory is customized, use the actual configured path.
2. Ask which backend to use (Pi or DSH), then which available provider/model. Show a short list derived from the actual local configuration and offer the existing default. If the user has already selected Pi + a named provider/model, resolve that choice directly. Ask a follow-up only when multiple model IDs fit the selection.
3. Keep credentials in the backend's existing authentication store. For a new service, direct the user to the backend's local sign-in/configuration interface. Do not ask them to paste secrets into chat. A custom service requires its exact endpoint, API protocol and model ID; credentials may be reused only for the same user-authorized service.
4. For Pi, store the selected provider/model in Bridge-specific configuration (`pi.provider` / `pi.model` per instance, or `BRIDGE_PI_PROVIDER` / `BRIDGE_PI_MODEL` in the Bridge launch environment). Keep the daily Pi/PiDeck default unchanged. For DSH, configure its own selected home/profile; the adapter rejects task.model overrides. Read [dsh.md](dsh.md) before changing a DSH route, and use a separate DSH_HOME if an existing home serves other users/tasks.
5. Review the worker capability choice. Default to inherit; when an explicitly intended bounded worker uses minimal loaders, retain required local machine-policy/shell/routing extensions through explicit paths. Explain that the worker's enabled tools change while global Pi settings remain unchanged. See [worker-profiles.md](worker-profiles.md).
6. Persist a non-secret installation record: actual runtime command, backend, provider/model, state root and loader choices. Generate MCP configuration in the same launch environment and retain its complete env section. An installation-specific reference may record local paths, but keep machine paths out of the published generic skill.
7. Check dependency discovery and RPC separately. If Pi startup is rejected before RPC events appear and diagnostics identify creation of the temporary `trust.json` lock under its agent state directory, request the host's narrow authorization for that directory's normal lock-file create/remove operation, then retry the same check. Keep the scope limited to the actual Pi state directory; do not change OS ACLs, disable approvals, or authorize unrelated home files. Once the startup check succeeds, use a fresh test instance and dedicated workspace for a real small task; wait for completion and require passed / verified plus independent verifier exit code 0. Report disabled or failed checks accurately. An MCP handshake alone does not establish model execution.

For a reinstallation, first identify the exact owned runtime/skill locations and check for active tasks. Stop only affected instances. Back up a custom skill/launcher before replacing it, retain authentication and backend data, and verify resolved paths before recursive removal. Avoid deleting shared Pi/DSH packages, another chat's state or user workspaces. Install the published archive into an empty Bridge-specific directory and test the installed copy rather than a source checkout.
